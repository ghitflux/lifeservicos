# Incidente 2026-04-20 — Sistema fora do ar (containers em estado Created)

## Resumo

**Data/Hora detecção:** 2026-04-20 ~11:30 BRT  
**Duração estimada:** Indeterminada (containers em estado `Created` desde último deploy em 12/04)  
**Impacto:** Sistema completamente inacessível — API e WEB offline, proxy retornando 502  
**Severidade:** Crítico  
**Resolução:** `docker compose up -d api web` — containers subiram em ~40s  

---

## Diagnóstico

### Sintomas observados

- `src-api-1` e `src-web-1` ausentes em `docker ps` (apenas `docker ps -a` os mostrava)
- `curl http://localhost:8000/health` — sem resposta
- `curl http://localhost:3000` — conexão recusada
- Proxy (Caddy) logando: `dial tcp: lookup web on 127.0.0.11:53: server misbehaving`
- `docker logs src-api-1` — sem output (container nunca iniciou)

### Estado dos containers

```
src-web-1   Created   ExitCode=0
src-api-1   Created   ExitCode=0
```

Estado `Created` significa: container foi **criado** mas nunca **iniciado** (`docker start` nunca foi chamado após o `docker create`).

### Causa raiz

O deploy de 2026-04-12 usou:

```bash
docker compose up -d --force-recreate --no-deps api web
```

O `--force-recreate` recria os containers (equivale a `docker rm` + `docker create`), mas em determinadas condições de dependência (healthcheck do db pendente ou race condition na inicialização), o compose pode completar sem efetivamente dar `docker start`. O container fica em `Created` sem erros visíveis no output do compose.

**Por que não foi detectado automaticamente:**

| Mecanismo | Por que falhou |
|---|---|
| `restart: unless-stopped` | Só age quando container **para após ter iniciado**. Estado `Created` (nunca iniciou) não aciona. |
| autoheal | Monitora containers **unhealthy**. Container `Created` nunca entra no ciclo de health check. |

O autoheal funcionou corretamente em 18/04 para uma situação diferente (API ficou unhealthy e foi reiniciada). Mas não cobre o caso de container que nunca iniciou.

---

## Resolução

```bash
docker compose up -d api web
# db também foi recriado por detectar mudança de config, sem impacto nos dados
```

Containers subiram saudáveis em ~40s. Nenhuma perda de dados.

---

## Correções aplicadas

### 1. Deploy script (`scripts/deploy.py`)

Adicionada verificação pós-restart: após o `--force-recreate`, o script verifica se algum container ficou em `Created` e força o `docker start` manualmente.

```python
stuck_created = [l for l in status_out.splitlines() if "Created" in l]
if stuck_created:
    for container in stuck_created:
        name = container.split()[0]
        run(ssh, f"docker start {name}")
```

### 2. Tempo de espera pós-deploy

Aumentado de 20s para 40s para dar mais margem ao healthcheck do db antes do api iniciar.

---

## Lacuna de monitoramento identificada

Nenhum dos mecanismos atuais detecta containers em estado `Created`. Para cobrir este cenário seria necessário um cron ou watchdog externo que verifique periodicamente se todos os containers esperados estão em `running`, não apenas `healthy`.

Opção simples via cron no servidor:

```bash
# /etc/cron.d/docker-watchdog
* * * * * root docker ps -a --format '{{.Names}} {{.Status}}' | grep -E 'src-api|src-web' | grep 'Created' && cd /opt/lifeservicos/src && docker compose up -d api web >> /var/log/docker-watchdog.log 2>&1
```
